# iOS evidence and free CI

Reference checked **2026-10-11**. Recheck official policies before enabling or dispatching CI and before each release. No iOS build or account entitlement is proved merely by installing this skill. “Apolygis” is an unverified service name; it might mean Appetize, but do not create an account, upload a build or assume a free allowance from that guess. Native GitHub/macOS simulator execution is the supplied route.

## Cost gate before any hosted execution

[GitHub Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions) currently says standard hosted compute is free for public repositories. Private repositories consume the owner's allowance; usage beyond it may be billed. GitHub Free currently includes 2,000 minutes/month and 500 MB artifact storage; Pro includes 3,000 and 1 GB. These are plan allowances, not the user's measured balance. Larger runners are charged even for public repositories. Artifact and cache storage have separate accounting; public compute alone is not proof of zero storage charges.

Do not encode the old “macOS is always 10x” rule as an entitlement calculation. The current [runner pricing table](https://docs.github.com/en/billing/reference/actions-runner-pricing) lists standard macOS at USD 0.062/minute and Linux 2-core at USD 0.006/minute for billable usage. Legacy multiplier descriptions are not a current quota guarantee. Inspect the owner's actual current plan/usage evidence before any private macOS proposal; unknown remaining quota means BLOCKED. This skill never reads payment methods, billing secrets or changes spending settings.

The supplied route avoids the storage ambiguity: it uses public standard compute and built-in job logs only, with no artifact/cache/package/LFS upload. Current GitHub billing examples explicitly exclude job logs and job summaries from artifact storage allowance. Screenshots are bounded and encoded into those logs, not sent to `upload-artifact`. Old community answers about unlimited public artifacts are not treated as current pricing guarantees. This is an explicit transport choice, not a recommendation to put private app/user data into public logs.

Any alternative that uses private compute or potentially billable storage needs the owner's verified existing applicable budget with an enforced zero-overage stop, rather than alerts alone; see [GitHub budget controls](https://docs.github.com/en/billing/how-tos/set-up-budgets). Do not enable billing, raise a budget or add a payment method. A timestamped owner-provided/native nonsecret quota and hard-stop result is evidence; an arbitrary repository variable is only recorded approval. Shared concurrent jobs can consume a quota after a check, so a quota estimate without an enforced stop is insufficient.

## Opt-in unsigned simulator workflow

The supplied [workflow template](../assets/ios-simulator.yml) stays outside `.github/workflows` in this tooling repository. Copy it only into the selected Flutter application's repository as `.github/workflows/ios-simulator.yml`, after reviewing that project's dependencies and authorization. It runs only by `workflow_dispatch`, only for a public repository, and only when its owner has set `STORE_AUTOMATION_PUBLIC_CI_APPROVED=true` to approve public source and synthetic test screenshots. It has no private/larger-runner override. Do not change repository visibility to obtain free execution; that would publish source and requires a separate deliberate decision.

Confirm visibility using native nonsecret `gh repo view OWNER/REPO --json visibility`; GitHub login alone proves neither entitlement nor quota. If public status or synthetic-public-data approval is absent, leave the variable unset and prepare files only. A skipped job is not an iOS pass. The workflow never inspects or changes billing configuration. Existing private app projects need local macOS or a separately reviewed quota-safe CI design; do not weaken the guard.

The template validates a repository-contained Flutter app directory, analyzes/tests it, runs `flutter build ios --simulator --debug --no-codesign`, selects an installed available iPhone simulator, boots/installs/launches the actual `.app`, and retains a screenshot with source/bundle/simulator/Xcode provenance. It uses the standard `macos-latest` runner and reports actual installed tools. No certificate, provisioning profile, Apple account or signing secret is needed for this simulator route. Flutter's [iOS setup](https://docs.flutter.dev/platform-integration/ios/setup) and [iOS release guide](https://docs.flutter.dev/deployment/ios) describe the separate environment and device/store release prerequisites.

Fetch the completed run's built-in logs using native `gh run view RUN_ID --repo OWNER/REPO --log` into a local temporary file; do not dump the base64 payload into model context. Use `python "<skill>/runtime/tool/ios-evidence.py" <local-log> <new-output.png>`. It extracts exactly one `STORE_AUTOMATION_PNG_BEGIN launch <bytes> <sha256>` block and collects its `STORE_AUTOMATION_PNG_DATA <base64>` lines through `STORE_AUTOMATION_PNG_END launch`, decode with strict base64 validation and require the declared size (at most 6 MiB), SHA-256 and PNG signature to match before exclusively writing the selected project's local screenshot path. Ignore GitHub's timestamp/job prefixes and reject missing, duplicate, truncated or mismatched blocks. Bind the local evidence to the actual repository/run/source SHA and inspect the resulting image. Logs may expire; fetch promptly. Never publish health/user data, account screens, secrets or real backend records through this route; use synthetic fixtures only.

A screenshot after launch proves only a simulator capture was produced. Review it for the actual app screen, errors and localization; then run project integration flows for launch stability, navigation, persistence, permissions, accessibility and selected modules. It does not prove physical-device behavior, purchase/reward callbacks, signed release performance, App Store acceptance or availability. Add an iPad/tablet run only when the product targets that form factor; screenshots must retain actual platform/locale/device provenance. App-specific startup and missing-plugin failures remain blockers, not reasons to replace evidence with Android screenshots.

## Fresh release gate

For each proposed release, record checked date, authoritative links, applicable requirement, actual source/artifact finding and remaining remote gate in that project's Brain task/evidence. Old PASS results do not carry across a changed SDK/dependency/permission set. Do not auto-edit targets just to satisfy a dated checklist without compatibility tests.

- **Apple tools and SDK:** Check [upcoming requirements](https://developer.apple.com/news/upcoming-requirements/) and the actual selected Xcode/SDK. On the reference date Apple requires uploads built with Xcode 26+ and iOS/iPadOS 26 SDK+, and lists iOS/iPadOS 13 minimum deployment targets. Simulator builds are not signed submission archives. Recheck age-rating questions and the selected app's remote status.
- **Apple privacy:** Audit app and transitive SDK data collection, tracking and required-reason APIs against [privacy manifests](https://developer.apple.com/documentation/bundleresources/privacy-manifest-files), [required-reason APIs](https://developer.apple.com/documentation/bundleresources/describing-use-of-required-reason-api) and [listed SDK/signature requirements](https://developer.apple.com/support/third-party-SDK-requirements/). Validate bundled `PrivacyInfo.xcprivacy` contents and actual App Privacy answers; a file existing is insufficient. Never invent an approved reason or assert no data collection from an empty manifest.
- **Google SDK:** Check the [current target API requirement](https://developer.android.com/google/play/requirements/target-sdk) for the actual form factor. On the reference date new phone apps/updates require API 36; other form factors and existing-app availability have different thresholds. An extension is not assumed. Verify the final merged manifest/AAB and test target-version behavior changes, not only a Gradle literal.
- **Google privacy and permissions:** Compare all app/SDK/backend behavior with [Data safety](https://support.google.com/googleplay/android-developer/answer/10787469), [permission declarations](https://support.google.com/googleplay/android-developer/answer/9214102) and [sensitive information policy](https://support.google.com/googleplay/android-developer/answer/16558241). Check least privilege, disclosures, consent/denial, retention/deletion and account deletion where applicable. Local JSON does not prove Console submission.
- **Health features:** Check [health declarations](https://support.google.com/googleplay/android-developer/answer/14738291) and [health categories/guidance](https://support.google.com/googleplay/android-developer/answer/13996367) against actual features and claims. All relevant Play apps must complete the declaration, including declaring no health features when that is accurate. Nutrition/weight tracking is health functionality. Do not infer medical-device approval, research consent or safe medical claims from a build/test result.

## Project-owned lifecycle

Use one project Brain and its existing test/build/publishing commands. A requested maintenance run first reads the selected project's unfinished tasks, current store versions and applicable policy changes; it does not import another app's queue. Apply only justified dependency/security fixes, run affected tests plus platform/visual gates, and obtain fresh independent review. Bump semantic version/build number only for an actual release candidate after comparing remote versions. Write truthful localized release notes from the final diff and retain source/artifact fingerprints.

Store preparation, internal testing, review submission and production are separate destinations. Existing exact app/account/operation authorization persists, but generic skill installation does not select a production app or grant billing/role/data-deletion operations. Reuse canonical AppPublishing/Fastlane references, keep secrets out of AI context, and block on missing store declarations/signing/account mapping. After an authorized write read back remote version/track/status; store review and rollout remain separate. Scheduling/monitoring is created only when requested; meaningful changes/failures/action needs should notify, unchanged state should remain quiet. No scheduler or store operation is enabled by this template.

Public CI does not grant access to private Git dependencies. Verify every dependency source before dispatch. Do not publish or vendor private shared source merely to make CI pass, and do not copy interactive credentials into a public job. Use appropriately licensed public sources or app-owned standard Flutter implementation where necessary; keep the existing private package repository private.
