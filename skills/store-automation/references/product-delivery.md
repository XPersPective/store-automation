# End-to-end product delivery

Use this protocol for a complete product, from discovery through supported distribution and maintenance. It defines required evidence, not a claim that every account, backend, media or store adapter is implemented. Reuse [lifecycle intake/stages](lifecycle.md), [publishing](publishing.md), [task personas](task-personas.md), and the mandatory catalogue/account preflight in SKILL.md. Decisions and tasks live in the selected project's Brain; do not add another product registry.

## Definition and architecture

1. Record the user's outcome, target users, core journeys, supported platforms/devices/locales, delivery destinations and concrete success criteria. Reuse confirmed choices. Resolve only missing choices that block the next gate, including exclusions, source/asset license, data needs, monetization, operating budget and exact release scope. Not every product needs a backend, auth, analytics, ads or purchases.
2. Audit existing source, actual call/data flow, platform integration and release evidence before planning. Map each journey to observable acceptance, including loading/empty/error/offline states, permissions denied, recovery and accessibility. Keep features outside the confirmed goal out of the plan.
3. Run [architecture review](architecture-review.md) before substantial implementation and again when integration changes invalidate its assumptions. Record the evidence-backed findings, alternatives and smallest viable solution in a project ADR; reuse existing components, native capabilities and dependencies before adding infrastructure.
4. Create executable tasks with exact source scope, risks, persona, bounded context/output and meaningful checks. Choose specialists from the catalogue: appropriate lightweight execution for bounded work, strong architecture/security review where risk requires it. Announce assignments and budgets before dispatch. Keep one app writer and fresh review after verified changes.

## Frontend and conditional backend

Design the real core journeys with a coherent existing or deliberately selected theme, responsive hierarchy, readable typography and localized content. Use available design skills when relevant; do not replace a user's selected theme without authorization. Implement keyboard/focus/navigation semantics, screen-reader labels, contrast, text scaling, touch targets and reduced-motion behavior. Verify on the actual supported device/OS/browser set and representative viewport sizes; screenshots alone do not prove interaction or accessibility.

Add backend/auth/cloud only when a confirmed journey requires it. Compare existing services and native/local alternatives against deployment/maintenance burden, documented free limits, overage behavior, security and data location. Research current official service terms when selecting a service; no paid API or billing activation by default. Record the selected service, trust boundaries, access rules, retention/deletion/export, offline/sync conflicts, rate limits and quota failure behavior. Check authorization on the server, validate untrusted input, and test cross-user access, session expiration, denied requests and safe recovery. Credentials stay in native stores or direct tool consumption by reference, never model context.

Implementation covers complete frontend/backend integration, appropriate input validation, error handling and platform behavior. Trace all callers of shared fixes. Use existing commands for relevant unit/integration/build checks; leave one runnable regression for nontrivial logic. Cover migrations/rollback and data-loss paths when present. Verify billing/receipts/restore, ads consent and account deletion only when included; unavailable store/device/account evidence remains a named blocker.

## Release candidate and marketing assets

Prepare a source-bound release candidate with identity/version/signature checks, dependency/license inventory, privacy/support/legal facts, real install/start/update checks and a recovery plan. Run machine checks and fresh independent review; resolve release blockers before submission. Keep platform-specific verification honest: Android evidence cannot certify iOS, and local preflight cannot certify remote signing, store compliance or availability.

Prepare localized store metadata and marketing material from the accepted product's actual capabilities and audience. Use concise, persuasive, specific copy: clear benefit, supported use cases, differentiators, truthful feature descriptions and useful release notes. Match each store's current locale/length/specification rules. Do not invent health/security/performance claims, awards, testimonials, ratings or unavailable features. Have a competent language reviewer inspect meaning, spelling, tone and consistency; automated translation alone is not acceptance.

Use actual platform screenshots from the reviewed build, with recorded source/build/device provenance. Produce polished crops, captions, feature graphics and optional preview video only where useful and allowed by the selected store. Preserve legibility, safe areas and locale consistency; inspect final decoded/exported assets at delivery size. Promotional compositions cannot substitute for actual app screenshots or device acceptance evidence. Use owned/licensed fonts, artwork, audio, stock and generated media with recorded origin/license/usage restrictions; verify rights to any recognizable brand/person. No automatic paid media generation or paid AI API. Use an authorized available tool, existing licensed assets or leave the missing asset gate explicit.

Store native metadata/assets in the existing canonical AppPublishing layout; reuse its Fastlane lanes. Local `release-preflight` checks public inputs only and returns PREPARATION_ONLY. Human/tool-required gates still include visual quality, factual claims, licenses, current store specifications, signature/embedded identity, real device behavior, privacy declarations and remote account/track evidence.

## Publication and operation

Existing exact app/account/operation/destination authorization persists. Generic skill installation or a product build request does not select a production account/track. Prepare all authorized reversible work first; if publication scope is missing, present the completed release candidate and request only that missing decision. Never guess declarations, read credentials, broaden roles, activate billing or run a production lane as a harmless test.

For authorized uploads use canonical native tools, then read back remote version/build, destination and status. Avoid duplicate uploads after interruption. Report submission, review and public availability separately, with the actual URL/version when available. A rejected submission creates a bounded evidence-backed correction task, then affected verification/review and authorized resubmission; external account/store/macOS blockers stop that gate while independent work continues.

After launch, use only approved privacy-respecting crash/performance/analytics collection; no tracking added by default. Define useful product signals and consent/retention rules, inspect real evidence, and avoid collecting sensitive content unnecessarily. Handle support, security incidents, dependency/SDK/store policy changes and reproducible defects through the same scoped task/check/review/release loop. Schedule recurring maintenance only when requested, for selected projects. A successful launch is a checkpoint, not proof of permanent correctness or unlimited service capacity.
